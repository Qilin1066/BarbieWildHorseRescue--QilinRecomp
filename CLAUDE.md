# CLAUDE.md

Static recompilation of **Barbie Horse Adventures: Wild Horse Rescue** (original Xbox, USA) to native code. Same requirements and scope as the sister projects Qilin1066/GBTGhoulies--QilinRecomp, ApbArcade--QilinRecomp, RhythmHeavenFever--QilinRecomp, PunchOutWii--QilinRecomp, WindWakerHD--QilinRecomp and ToyCommander--QilinRecomp (the owner's instruction, 2026-11-21: "exact same as the other projects, in scope and requirements ... even down to the same enhancements menu"). This repository is Qilin1066/BarbieWildHorseRescue--QilinRecomp (until 2026-11-21 Barbie-Wild-Horse-Rescue---QilinRecomp: the owner renamed every QilinRecomp repository that day to `<Game>--QilinRecomp`, BeatTheBeat becoming RhythmHeavenFever; the sisters' own documents may still use their old names, and newer sisters exist: ToyRacer, RidgeRacer7, MetropolisStreetRacer). **GBTGhoulies--QilinRecomp is the same console and is the model**: when a design question here is undecided, do what it did, and take its code (same owner, same licence) rather than writing it again. The claude.ai Project "Barbie Horse Adventures: Wild Horse Rescue Recomp" holds a short status note (`claude/status.md`); this file and `docs/` are the full record.

## Requirements (non-negotiable)

- **Efficiency first, then accuracy, and fail loudly.** Never paper over an unknown: stop with a clear error (an error message and exit code in the tools, `rt::Stop` in the runtime, CMake `FATAL_ERROR`).
- **C++23** everywhere: recompiler, runtime and generated code.
- **Vulkan 1.3 only** for graphics. No OpenGL, D3D or Metal backends (macOS goes through MoltenVK).
- **Static recompilation only.** No interpreter, JIT or emulator at run time, not even as a fallback.
- Targets: 64-bit **Windows, Linux, macOS** on **x86-64 and ARM64**. The low-end reference is ARM boards like the **Raspberry Pi 4**. No 32-bit.
- Compiler minimums: GCC 14, Clang 19, Apple Clang (Xcode 16), MSVC 2022 17.10.
- **Licence: GPL-3.0** (`LICENSE`), by the owner's choice for all the QilinRecomp projects (2026-11-21, in place of MIT; the owner's commit is the first after the initial one).
- Nothing copied from an emulator: xemu and Cxbx-Reloaded's emulation code are run or cited, never read into this code (the sister projects' rule, which their change of licence left standing; XbSymbolDatabase is MIT and is used as GBTGhoulies uses it). Keep dependencies to the fewest possible (the owner's standing preference); third-party libraries are permissive and handled as GBTGhoulies handles them (vendored, listed in `third_party/README.md`; SDL3 fetched by CMake, pinned).
- **Nothing about the game is assumed from the other game.** Its code and methods come over; its addresses, regions, counts and conventions describe another executable. Every such fact lives in `recomp/src/game.hpp` and is put there only from an analysis of this game.
- Never commit game data or anything derived from it: the disc image, `default.xbe`, extracted files, `analysis-out/`, listings, import lists made from the binary, `gen/`, `cfg.json`. These are gitignored.

## Layout

- `recomp/src/`: `xiso` (Xbox disc images), `xbe` (the loader; `xbe_json.cpp` its JSON), `sha256`. These three are CMake's `qilin_xbe`: **runtime code too, so no `std::format` in them** (`strf.hpp`). `decoder` (Zydis wrapper), `cfg` and `vrange` (function discovery, control flow, jump-table sizes, coverage), `lifter`, `game.hpp` (the supported build: every game-specific table, all empty until the analysis), `regions.hpp`, `json.hpp`, `kernel_exports.inc` (generated by `tools/gen/kernel_exports.py` from nxdk's list), `main.cpp` (the `qilin` CLI). `qilin_core`: tools only.
- `recomp/runtime/`: `guest.hpp` (context, memory, flag and float helpers), `x87_math.hpp`, `strf.hpp`, `dispatch.cpp`: what lifted code compiles against.
- `recomp/runtime/gfx/` (the Vulkan renderer, `qilin_gfx`), `audio/` (voices and the mixer, `qilin_audio`), `platform/` (window, input, sound output on SDL3, the settings file `wildhorserescue.ini`; `qilin_platform`), `ui/` (the settings menu, `qilin_ui`; `menu_preview.cpp` is `qilin_menu_preview`, the menu over a test card): GBTGhoulies' (v0.41.2), console-level, with the game's name changed and nothing else but what `CHANGELOG.md` 0.2.0 lists. Keep them in step with GBTGhoulies: a fix there belongs here and the reverse. 
- `recomp/runtime/host/`: `host.*` (the replacement registry, reports), `guest_ram.cpp`, `kernel.cpp`, `kernel_crypto.cpp`, `kernel_io.cpp`, `sched.*`, `call_guest.cpp`: GBTGhoulies' (v0.41.3), unchanged but for an empty `xdk_symbols.inc`. `run.cpp` is `qilin_run` and is **this project's own**: it calls the XBE's lifted entry point (`docs/runtime.md`), where GBTGhoulies' calls its game's start-up by address. `d3d.cpp`, `dsound.cpp`, `xinput.cpp` came over from GBTGhoulies function by function against this game's XDK build (v0.7.0 on; since v0.13.0 no sister-build address is left in them); `aspect.cpp`, `game_hooks.cpp` and `game_native.cpp` are this game's own.
- `recomp/src/build.hpp` (the build's name, SHA-256, code regions: what the runtime may include) and `game.hpp` (the tools' part); `game_file.*` (default.xbe from an image, a folder or a file).
- `recomp/tests/make_test_xbe.cpp`: the hand-assembled test programs; `qilin_add_program(name expect)` in `CMakeLists.txt` lifts, builds and runs one (its lift must fit one `lifted_000.cpp`: under 200 functions).
- `recomp/tests/tests.cpp`: unit tests on a synthetic XBE and disc image. `qilin_tests --write-xbe <file>` writes the synthetic XBE for the `qilin_tool_*` tests, which run the CLI on it.
- `recomp/runtime/host/aspect.cpp` (widescreen: the engine's projection widened) and `game_hooks.cpp` (the native code run before or after the game's own functions: `game.hpp`'s `before_entry` and `after_return`) are this game's own.
- `tools/player-kit/` (the Windows download CI builds: `package.sh`, `play.ps1`, `README.txt`; `.github/workflows/player-kit.yml`) and `tools/build-wildhorse.ps1` with `Play Wild Horse Rescue.bat` and `Update Wild Horse Rescue.bat` (building from a clone with Visual Studio): from GBTGhoulies', with this game's names, disc check (`qilin info` says "build: the supported build"; the folder has `Packages` and `Video`) and runner arguments (`WildHorseRescue.exe "<disc folder>"`). Never run on Windows by this project yet.
- `tools/difftest/`: the differential test (v0.12.0, `docs/recompiler-core.md`).
- `tools/check/`: `verify_decoder.py` (Zydis against LLVM, on `qilin insns` listings of the game), `x87/` (rounding and transcendental checks, no game needed).
- `tools/analyse-game.ps1` and `Analyse game.bat`: build `qilin` on Windows and write the first analysis to `analysis-out/`. Keep the script Windows PowerShell 5.1-compatible and ASCII-only. **Never run yet.**
- `docs/`: design and results. Keep them current. `runtime.md` is the runtime and `qilin_run`'s design; `graphics.md` the Direct3D layer's port (in progress); `roadmap-and-design-targets.md` is the roadmap, every design target and the settings menu's layout (parts that depend on the executable are marked **to confirm**); `xbe-analysis.md` is where the first analysis goes; `recompiler-core.md` what the tools are, what was changed from GBTGhoulies and which of its heuristics must be measured here; `prior-art.md`; `naming.md`.

## Build and check

```sh
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release -DQILIN_WERROR=ON
cmake --build build --parallel 2
ctest --test-dir build --output-on-failure
build/qilin info <game>          # <game>: the disc image, an extracted folder, or default.xbe
build/qilin imports <game>
build/qilin cfg <game> && build/qilin align <game> && build/qilin coverage <game> --list
```

Before a milestone commit: tests pass, warnings are clean (`QILIN_WERROR`) under two compilers locally, and CI is green on all six configurations. Check CI after pushing (its results are readable without signing in: `https://api.github.com/repos/Qilin1066/BarbieWildHorseRescue--QilinRecomp/actions/runs`; compiler messages are annotations on the commit).

## Known facts worth not rediscovering

- **The game:** the owner's dump is an extracted disc beside the `.iso` on the owner's PC (its path is in the Project's `claude/status.md`, never in this repository). A session asks for access to that folder (`device_request_folder_access`) and stages `default.xbe` (2.4 MB); the `.iso` (588 MB) is over the staging limit. Everything in `docs/xbe-analysis.md` came from that file.
- The supported build: SHA-256 `51e6aa2a…7e4` in `build.hpp`. Since it is recorded, anything run on a synthetic or test XBE needs `--any-build` (the CMake tests pass it).
- First results (v0.4.0): XDK 5558; no XACT, no Bink, movies are XMV; 120 kernel imports, 36 without native code (mostly the hardware libraries'); `.text` is laid out as the sister game's (aligned game code `0x11000`–about `0xE9000` and about `0xF0000`–`0x146000`, unaligned XAPI between and C runtime after, EH funclets last); 5,844 of 5,899 functions lift, the failures listed by reason in `docs/xbe-analysis.md`.
- `qilin lift` on the whole game takes about 4 seconds; if it runs for minutes, something loops (v0.4.0 fixed one such loop).
- To build and run the game in a cloud session: stage `default.xbe`, `qilin lift <xbe> --out <gen outside the repo>`, `cmake -B build-game -DQILIN_GEN_DIR=<gen> -DSDL_WAYLAND=OFF`, `cmake --build build-game --target qilin_run --parallel 2` (about six minutes with GCC 14), then `qilin_run --data-dir <dir> <folder holding default.xbe>`. v0.7.0's run (with `--mute` where there is no sound device) stops at the first Direct3D call. `QILIN_TRACE_HLE=1` logs every native call.
- Before registering a library function natively, check its argument bytes in this build (the `ret n` of the function at the symbol's address in a `qilin insns --linear` listing): the sister project's values are for another XDK build. v0.7.0 did this for every DirectSound function the game calls.
- Reading the game's code in a session: `qilin insns <xbe> --linear -o linear.insns.txt`, then a few lines of Python that print the instructions from an address with the symbols' names substituted (v0.7.x used this for every Direct3D fact in `docs/graphics.md`). Neither the listing nor notes quoting it go in the repository beyond the addresses and what the code does.
- XbSymbolDatabase in a cloud session: `git clone --recurse-submodules https://github.com/Cxbx-Reloaded/XbSymbolDatabase`, check out `20eced5`, `cmake -S . -B build && cmake --build build`, then `python3 tools/gen/xdk_symbols.py <build>/projects/cli/XbSymbolDatabaseCLI <default.xbe>` (it is run, never read into this code beyond its MIT-licensed names).
- The bring-up loop: run, read the stop, provide it, run again. A stop inside the kernel names the function and what isn't modelled; `QILIN_TRACE_HLE=1` shows the calls before it with their arguments and callers, which is how a caller is found and read (`qilin insns --linear` listing) before anything is implemented.
- Regions, conventions and natives: `docs/code-analysis.md`. The engine is Blitz Games' "Babel" (`bk`/`bd`/`ba` functions, `xb*.cpp`); its strings name functions and files, which helps find the frame clock, the display set-up (`bdOpenDisplay`) and the XMV player (`bdVideoPlayXMVStream`).
- A cloud session reaches the PC only while the Claude desktop app is open there, and in the sister projects' sessions it could list and stage files (up to 400 MB each) but had no shell. A disc image is larger than that: have `Analyse game.bat` run on the PC, then stage `analysis-out/` (small) and `analysis-out/extracted/default.xbe`. If the owner has an extracted disc, `default.xbe` can be staged directly.
- After a repository is renamed, a cloud session's access is to the old name: `gh` and pushes answer 403 about numeric-ID paths until the new name is added to the session (`add_repo`) and the remote's URL is changed. `gh run list` fails the same way; use `gh api repos/<owner>/<repo>/actions/runs`.
- Tags don't reach GitHub from a cloud session (the proxy refuses pushing them); `main` does. Releases are marked by their commit's title (`vX.Y.Z: ...`) and the changelog.
- The cloud workspace (Ubuntu 24.04) has GCC 13 and Clang 18 installed, both below the minimums. `apt-get update && apt-get install -y g++-14 gcc-14` gets GCC 14; for Clang, `pip install ziglang` and wrapper scripts running `python3 -m ziglang cc` / `c++` as `CMAKE_C_COMPILER` / `CMAKE_CXX_COMPILER` (zig's Clang is 22). v0.1.0 was built warning-free with both. MSVC and Apple Clang are checked only by CI.
- GCC's `-Wshadow` also flags a local reusing a file-scope name (Clang's and MSVC's don't), and MSVC's `[[maybe_unused]]` covers only a declaration's first declarator: both bit the sister projects. Don't name locals `far`, `near` or `huge` (old MSVC macros in Windows headers). MSVC's C4127 (an error under `/WX`) fires on a condition built from `game.hpp`'s `constexpr` values: what code asks about at run time (`kSha256`) is a plain `const` there.
- The tools came from GBTGhoulies v0.41.1. Its CFG pass carries heuristics measured on that game (16-byte function entries for data-pointer and gap seeding, the data sections known by name, "implausible instruction" rules): `docs/recompiler-core.md` lists them. Run `qilin align` and read `coverage --list` before believing a function count.
- To drive the game in a headless run: `qilin_run --headless --dump-frames DIR --press "2300:start/10,2700:a/10,..." <folder>` (frames as shown, movie frames included: the title screen is about frame 2100). Dumped frames fill the disk quickly (30,000 frames is about 20 GB): use `--frames N` and delete what isn't needed. `QILIN_TRACE_DRAWS=a,b` logs every draw of swaps a to b (a swap is two frames shown at 30 fps, one at 60: in play the swap number runs about 600 behind the frame), `QILIN_TRACE_MATCH=x|y` keeps the lines containing one of them, `QILIN_TRACE_DETAIL=1` adds each draw's combiners, lighting, fog and first vertices (with `QILIN_NO_VERTEX_CACHE=1`, or the cached streams' vertices aren't shown), and `QILIN_DUMP_TEXTURES=DIR` writes every texture as it's uploaded (`<texel address>_<format>.pam`); a debugger on `qilin::rt::trap` gives the chain of lifted functions (`fn_XXXXXXXX`) at a stop.
- The game's language: this US build always sets 10 (US English) through `0x321C0`; the language setting goes in there (`game_hooks.cpp`). The game's object keeps it at +0x80, which also picks the loading screen's package (German: `loadingG`, not on this disc: the US one stands in, `add_disc_fallback`). Voices are English in every language. Settings files written before v0.13.0 had no effect on the language (the runtime never read it).
- The widescreen and HUD code is checked by frame dumps at another shape: a data folder whose `wildhorserescue.ini` has `aspect = 32:9` (dumps are 640×480: stretch them to the shape to look at them). `aspect = 4:3` must give frames identical to before.
- **Use `--virtual-time` for scripted runs** (v0.10.0, `docs/runtime.md`): time moves only as the game does, so a run with the same presses gives the same frames every time and a script can be built up a step at a time. In virtual time: the title screen ~2400; `2450:start/10,2700:a/10,2950:a/10,3200:a/10` reaches the dressing room (~3400); `3700..3860:down/6` (five, 40 apart), `4000:a/10`, `4300:a/10`, `4600:a/10`, `4900:a/10` chooses Blossom; `5200:b/10` rides into the yard (~5400). Then `5500:lu/230` rides to the gate, `5800:y/10` dismounts, `6050:ll/10,6150:ll/10,6250:ll/8` walks to the stable hand (a "Talk" prompt from ~6000), `6300:a/10` talks to her (voiced, no subtitles; another A starts the talk again). The pause menu offers a trail only once it is unlocked ("Explore next trail").
- Scripts that reach places in real time (frames as shown; times drift from run to run): the title screen ~2100; `2300:start/10,2700:a/10,3100:a/10,3500:a/10` reaches the dressing room (~4000), then `4300..4460:down/6` (five), `4600:a/10`, `5000:a/10`, `5400:a/10`, `5800:a/10` reaches the stables and chooses Blossom, `6200:b/10` rides out into the yard. Mini-games: `2300:start/10,2600:down/6,2650:down/6,2750:a/10,3000:start/10`, then A every 300 frames from 3300, starts a race at about frame 4800 (needs `Packages/Multi`). From the games list (A at 3300), `down` 0 to 3 times picks The Races, Coin Roundup, Lasso Challenge or Seagull Beach; A at 3800, 4100, 4400 starts it (each plays to its results screen by about frame 7000 with the sticks held). Runs started side by side load more slowly and fall out of step with their presses: run them one at a time.
- GBTGhoulies' runner sets the first thread's x87 control word after the scheduler copies its registers for later threads (fixed here in v0.8.x: threads started with a zeroed word); worth fixing there.
- GBTGhoulies' coverage unit test never counted an unknown byte (its region didn't fit the synthetic section); fixed here, worth fixing there.
- `qilin_tool_*` tests pass by their output (`PASS_REGULAR_EXPRESSION`), not their exit code: `coverage` exits 3 on the synthetic XBE by design (seven bytes of helpers nothing calls).
- XISO: sector 2048 bytes; the volume descriptor is sector 32 of the game partition, with the 20-byte signature at both ends, the root directory's sector and size after the first; directory entries are a binary tree (left and right offsets in four-byte units, 0 or 0xFFFF for none), with sector, size, attributes (0x10 a directory), name length, name. The game partition starts at 0x18300000 in a full dump of an original Xbox disc, at 0 in an image of the partition alone. Written from the public description; the real disc will confirm it.
- Facts about the game (Blitz Games, Vivendi Universal Games, North America, November 2003, also on the PlayStation 2) are from public descriptions, not from the executable. Nothing is known yet about its XDK version, libraries, video format or engine.
- The settings menu is GBTGhoulies' item for item (`docs/roadmap-and-design-targets.md` has the list) and is in since v0.2.0. Since v0.13.0 every entry acts on this game: the aspect and HUD (`aspect.cpp`, `d3d.cpp`), the frame rate ("Original" is the game's own: vsync, 60 at most), the language (the five console languages the disc has tables for).
- To try the window and menu in a cloud session: `apt-get install -y xvfb imagemagick mesa-vulkan-drivers` and the X11 headers CI lists; configure with `-DSDL_WAYLAND=OFF` (the workspace's Wayland headers are older than SDL 3.4's); `Xvfb :99 -screen 0 1280x800x24 &`, then `DISPLAY=:99 VK_ICD_FILENAMES=/usr/share/vulkan/icd.d/lvp_icd.json build/qilin_menu_preview --open-menu`, and `import -window root shot.png`. SDL's archive downloads from GitHub's releases through the proxy.
- After editing `CMakeLists.txt`, run `cmake -S . -B build` again before building one target by name: `cmake --build --target new_target` on a stale tree says there is no such rule.
- In the v0.2.0 session a request for access to the PC's Downloads folder was refused by the session's own permission rules, not by the owner: the owner has to connect the game's folder from the desktop app ("Add folder").

## Conventions

- **Push without asking, as in the sister projects (the owner's standing permission), but only what is 100% legal and above board to share with the world, checked before every push:** audit every unpushed commit (every path added, binaries, anything named like game data or game-derived output, copied third-party text or code, personal details such as the owner's local paths, name or e-mail). No game data or anything derived from it, no copied third-party text or code beyond the permissively licensed libraries listed in `third_party/README.md`. If anything fails the audit, fix it first; never force-push published history.
- Work on `main`; push with `git push origin main`. Releases are `vX.Y.Z`; the version lives only in `project(... VERSION ...)`. Every release gets a `CHANGELOG.md` entry (Keep a Changelog); never rewrite past entries.
- Prose in docs and commit messages: plain, specific, British spelling.
- UI conventions are shared with the other Qilin recomps (`docs/naming.md`, `docs/roadmap-and-design-targets.md`): keep them in step when either side changes.
