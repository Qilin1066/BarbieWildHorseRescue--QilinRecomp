# Graphics: Direct3D over the Vulkan renderer

`recomp/runtime/host/d3d.cpp` is GBTGhoulies--QilinRecomp's Direct3D layer (v0.41.3; its `docs/graphics.md` describes the design), brought to this game's XDK build (5558; the sister game's is 5659). This file records what that has established, so the work continues from facts and not from the other game's addresses.

**Where it stands:** the device starts, the window opens with the settings menu over it, and the game draws its start-up screens (the legal notice, the Barbie Software, Vivendi Universal Games and Blitz Games logos) and plays the intro movie through the video overlay, with its sound. It reaches the title screen and stays there, animated. Every address `d3d.cpp` takes from the sister build and that has not been found here yet is written `unlocated(sister's address)`: reaching one stops the runtime, naming it, so nothing is read or written at the other game's address. Every replacement is registered by name, and its argument size is checked against this build's code (`xdk_ret_bytes.inc`, generated by `tools/gen/xdk_ret_bytes.py`): a function whose arguments differ stops the runtime before it can unbalance the stack.

## What the design needs from the build
`d3d.cpp` keeps the library's state tables in guest memory in the original layout (the game writes render and texture-stage states inline), lifts the library's pure resource code, and replaces what drives the GPU. It therefore depends on about 110 addresses: the library's globals, fields of its device object, a few of its constant tables, and some forty of its functions. Each must be found in this build.

## Findings

### The same source, linked in another order
- **The device object's fields are where the sister build has them**, at every one checked by reading this build's code: the fence (`+0x2C`, `D3DDevice_SetRenderTarget`), the vertex shader (`+0x790`, `D3DDevice_SetVertexShader`), the reference count (`+0x934`, `D3DDevice_Release`), the depth range and format (`+0x944`, `+0x948`), the render target and depth buffer (`+0x19F4`, `+0x19F8`), the frame buffers (`+0x1A04`, `D3DDevice_GetBackBuffer2`). The device is 0x924 dwords (`D3DDevice_Release` clears that many).
- **The library's functions are in a different order** (the offset between the two builds' addresses changes from function to function, and is even negative for some), so no function address carries over by arithmetic.
- **The state tables keep their layout and move together**, by `0xA0C0` from the sister build's, wherever a symbol or this build's code confirms it:

### What differs between the builds
`D3DDevice_SetVertexShader` here loads and selects a programmable shader through `D3DDevice_LoadVertexShader` and `D3DDevice_SelectVertexShader`; the sister project's notes describe its build's differently. So the library's code is not identical between the two XDKs, and each function `d3d.cpp` mirrors ("as the original does") has to be read here before its mirror is trusted.

- **`D3DDevice_Swap`'s flags:** here `0` means `D3DSWAP_COPY | D3DSWAP_FINISH` (5). With a flipping device (`D3DSWAPEFFECT_DISCARD` or `FLIP`, which is what the game makes: swap effect 1), `COPY` does nothing and `FINISH` flips; the copy is only for a copy-swap or anti-aliased device, whose separate front buffer the library fills (device flag `0x4000`). The game ends each frame with `Swap(1)`, a callback, then `Swap(4)`. `D3DSWAPEFFECT_COPY` and anti-aliased multisample types stop the runtime.
- **The fixed-function pipeline:** this game's unlit draws carry normals (`D3DFVF_NORMAL`, ignored without lighting) and texture transforms (`D3DTSS_TEXTURETRANSFORMFLAGS` with `D3DTTFF_COUNT2`/`3`, or `PROJECTED` with `COUNT3`/`4`), which the sister game's don't; both are now in the generated vertex program. A stage that reads a texture with none set reads the hardware's no-texture value, (0, 0, 0, 1).

### What the game uses
From the stubs (`docs/code-analysis.md`): 48 functions. No index buffers and no `DrawIndexedVertices`; `DrawVertices` and `DrawVerticesUP`; vertex shaders the engine generates (`baGenerateShader`), with `SetVertexShaderConstant1`/`4`/`NotInline` and `SetShaderConstantMode`; fixed-function lights and materials are also set (`SetLight`, `LightEnable`, `SetMaterial`, `SetTransform`); palettes (`SetPalette`, `D3DPalette_Lock2`), which the sister game doesn't use; the overlay for movies; `PersistDisplay`. Functions the sister project replaces that this game never calls (pixel shaders by `CreatePixelShader`, `BeginPush`/`EndPush`, immediate mode, fences, `SetModelView`) can wait.

### Movies
The game plays its movies with Microsoft's XMV library, which is linked in its own section (`0x1DAD60`–`0x202B3C`) and is lifted whole: the decoder is the original's, MMX and all. What it calls is the native layer's: XAPI's overlapped reads with completion routines, a DirectSound stream (`DirectSoundCreateStream`) whose packets carry the presentation time in their context, `Pause(2)` and `SynchPlayback` to start the sound, `GetDisplayMode` for the refresh rate (60 Hz here) and `GetDisplayFieldStatus` for the vblank count it times frames by, and the video overlay for the pictures. The overlay is composed into the frame buffer being shown, over the frame the game last presented, and shown at once; `GetOverlayUpdateStatus` reports an update taken at the next vblank, as the hardware does. Its colour conversion is BT.601 video range, nearest-pixel scaling.

## Plan
1. **Past the title screen**, into the front end's menus and the first ride.
2. **The rest the game calls:** lighting through the fixed-function path (the vertex program has none yet: lit draws stop), `PersistDisplay`, `KickPushBuffer`. Palettes, `SetShaderConstantMode` and `D3DResource_BlockUntilNotBusy` are in (`SetPalette` and `SetShaderConstantMode` mirror this build's `0x168350` and `0x16AE60`).
3. Each mirror of the library's code that the run reaches, checked against this build before it is trusted (`SetVertexShader`, `SetRenderTarget`, `SetTransform`, `SetScreenSpaceOffset` and `SetTextureState_TexCoordIndex` have been).
4. The game-specific parts of the sister project's file (its frame clock, its HUD and aspect code) have no counterpart here yet: the frame clock and the projection are to be found in the engine (`docs/roadmap-and-design-targets.md`, steps 7 and 8). Until then only the original frame rate and 4:3 apply, and the settings that change them have no effect.
